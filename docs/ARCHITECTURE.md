# Архитектура и переиспользование CUDA-ядра

## Текущая схема

- **Хост:** Rust (рекомендуется) или C++. Конфиг, HTTP, XPartManager, очередь результатов, вызов GPU.
- **Ядро GPU:** C API в `cuda/keyhunt_capi.h` и `cuda/keyhunt_capi.cpp`. Линкуется с `ecc_cuda` (ECC, hash160, поиск по целям).
- **Использование:** keyhunt-pvk — поиск по hash160 (private key → hash160), итерации по X-part с сервера или из конфига.

## Переиспользование ядра

Ядро сделано так, чтобы его можно было использовать в других проектах без копирования ECC/hash160:

1. **Один C API слой** — все вызовы к CUDA идут через `keyhunt_capi`. Типы (KeyhuntHash160, KeyhuntSearchResult и т.д.) единые.
2. **Другие бинарники/проекты** могут:
   - линковать ту же `keyhunt_cuda_capi` и вызывать те же функции (keyhunt по hash160);
   - при необходимости добавить **новые C API-функции** в тот же или отдельный заголовок (например, для mnemonic-hunter), используя тот же `ecc_cuda` и при необходимости общие ядра.
3. **Утилиты на Rust** (decrypt_results, convert_hash160_to_binary, gpu_info) не зависят от keyhunt CUDA lib; общий код (формат results.enc, hash160 hex/bin) живёт в библиотеке keyhunt-pvk и переиспользуется.

## Варианты расширения

- **Mnemonic-hunter:** новый бинарник (Rust или C++), новый C API-модуль поверх того же или расширенного CUDA-кода (например, генерация ключей из mnemonic на GPU), без дублирования ECC.
- **Другие сценарии:** новые точки входа в C API и соответствующие хосты, общее ядро остаётся одним.

## Сборка ядра

Цель CMake: `keyhunt_cuda_capi`. Выход: статическая/динамическая библиотека в `build/cuda/`. Rust подхватывает её через `KEYHUNT_CUDA_LIB_DIR` и фичу `cuda`.
